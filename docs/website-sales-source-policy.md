# Продажи с сайта: аудит и правила источника заказа

## Аудит до изменения кода

База реализации: `239d7bd`, CRM0.1.63. ТЗ: `YO_CRM_Website_Sales_Codex_TZ.md`; эталон — утвержденное дополнение к существующим трем страницам. Деплой и изменение производственных записей не разрешены этим этапом.

1. **Существующие поля.** `Order.sourceSystem/sourceAccount/externalId` — происхождение импорта и стабильная внешняя идентичность, а не признак сайта. В KeyCRM `sourceAccount` является connectionKey. `Order.externalData` сохраняет исходный KeyCRM order, в том числе `source_id`. `Activity` типов `KEYCRM_ORDER_IMPORTED/KEYCRM_ORDER_SYNCED` сохраняет metadata `{keycrmOrderId,sourceName}` в той же транзакции, что и заказ. Это источник оформления самого заказа, в отличие от `Client.source` и Conversation.channel. Тип OrderType используется для правил производства/депозита; его нельзя массово менять ради аналитики.
2. **Пути поступления.** Найден импорт KeyCRM (`keycrm-normalizer.ts`, `keycrm.service.ts`) и авторизованное создание сотрудником (`orders.service.ts`). Прямой доказанный checkout endpoint yoleotard.com пока не найден. В сохраненном рабочем API-снимке08:33UTC все500 неархивных заказов имеют CUSTOM_ORDER/KEYCRM. Эти признаки сами по себе не показывают сайт.
3. **История и дубли.** Все доступные события импорта должны подтверждать один источник и совпадающий keycrmOrderId/externalId. WEBSITE требует прямого ограниченного домена/URL yoleotard.com в сохраненном источнике либо подтверждённого владельцем scoped alias (см. ниже); ни оплаты, email, клиентский Instagram, tracking, ни просто KEYCRM не являются доказательством. Неясные/противоречивые записи — UNKNOWN. Ручное происхождение подтверждает локальный ORDER_CREATED сотрудника при отсутствии внешней идентичности. Стабильный Order.id считается один раз; существующий unique(sourceSystem,sourceAccount,externalId) защищает повторный upsert. Отдельные исторические дубли не объединять автоматически.
4. **Деньги.** FinanceReportService/buildFinanceReport считает только неvoid Payment по receivedAt, не стоимость новых заказов. Валютный отчет использует существующий официальный свежий NBU/ECB cache, rational integer half-up и valuationVersion; это текущая оценка отчета, не выдуманный исторический курс. appliedAmountMinor/appliedCurrency остаются фиксированным распределением платежа на заказ. Расходы/инвойсы/остатки и правила приема/отмены платежей не меняются. Статус REFUNDED не является отдельной возвратной транзакцией: отсутствие такого ledger не позволяет придумывать отрицательное поступление. Отмена заказа сама по себе не аннулирует реально сохраненный Payment; существующее исключение void сохраняется.
5. **Совместимые расширения без миграции.** Добавочные orderSource/source analytics поля в Orders/Overview/Finance read projections; валидируемый source query. Старый /orders list без пагинационных параметров сохраняет массив для consumers, новый paged read возвращает строки и полные серверные счетчики. Финансовые таблицы/экспорт фильтруются источником связанного заказа; KPI и исходные диаграммы сохраняют существующую область. Новые аналитические проекции не добавляют в браузер raw externalData или provenance metadata; существующая история Details сохраняется совместимой. Контроллеры сохраняют guards/RBAC.

## Предварительная политика выборки

Неархивные заказы входят в количественную аналитику по createdAt (UTC-месяц, как в действующей CRM), включая отмененные с доступным исходным статусом; действующий график статусов остается доступен. Поступления — по receivedAt и исходной валюте операции, включая связанные архивные/отмененные заказы, пока платеж действителен. Запись без связанного или доказанного источника — UNKNOWN. Сегменты суммируются после индивидуального преобразования в выбранную валюту; одна операция учитывается один раз по Payment.id. Никакого импорта, переклассификации сохраненных записей или списания долгов.

## Проверки

Тестовые границы уже заданы обязательными11сценариями ТЗ: публичный нормализатор, реальные серверные read-service/report функции с удвоением только DB/provider boundaries, действующие guards и UI с настоящими переходами. Не заменять runtime финансовые данные фикстурами. Синтетические данные допустимы только в тестах; фактическая выборка и неопределенные исторические заказы будут отражены отдельно после чтения provenance.

## Подтверждённое владельцем соответствие и фактическая сверка

2026-10-15 владелец подтвердил: источник KeyCRM «Вебсайт», ID12, означает yoleotard.com. Правило закреплено одновременно за неизменной идентичностью текущего подключения (`sourceAccount`), raw source_id12 и точным сохранённым sourceName. ID12 из другого подключения не переносит это доверие автоматически. Это кодовое read-only соответствие, не изменение Order, типа заказа или данных KeyCRM.

Снимок09:54UTC, PostgreSQL READ ONLY + RepeatableRead: 500 неархивных заказов =21 WEBSITE +155 INSTAGRAM +324 OTHER; MANUAL/UNKNOWN=0. В октябре создано6, из них3 WEBSITE (50%). Получено в октябре312368 minorEUR; WEBSITE122031, Instagram140500, OTHER49837. Валютные разрезы сверены с тем же текущим valuation snapshot. Это состояние базы CRM, а не свидетельство полноты внешнего KeyCRM или банковской сверки.

Доказательство классификации консервативно: ORDER_CREATED вместе с внешним импортом, MATCHED_EXISTING, несовпадающие внешние ID, пустые/противоречивые sourceName возвращают UNKNOWN. Читается максимум101 provenance-событие; при более100 UNKNOWN, чтобы неполный хвост истории не выдавался за доказанное происхождение. Исторические записи при этом не меняются. Данная граница должна учитываться при росте числа синхронизаций; стабильная агрегированная provenance-проекция — возможное отдельное улучшение. Пустая нативная история не доказывает ручное происхождение.

## Контракты чтения и навигации

- `GET /orders` без page/pageSize сохраняет массив; с пагинацией — items/total/page/pageSize/metrics/sources/disciplines/focusFound. Поиск и существующий Overview-контекст применяются до source. Счётчики и facets покрывают весь соответствующий серверный набор. Narrow кандидаты читаются батчами500, rich relations — только для page IDs. Сортировка и selection исполняются на сервере; это линейный aggregate-pass без массовой rich hydration, не индексированный SQL materialized view.
- Source count в Orders относится к поиску/периоду до source; KPI исходных фильтров — к выбранному source до quick/status/discipline, как раньше. Количественные месяцы — UTC, операционные дни — Europe/Kyiv, согласно существующим правилам.
- Overview получает агрегированные корзины по созданию, не список заказов. В 0.2.0 справочник расширен до сайта, ручного / CRM, Instagram, Facebook, чата, WhatsApp, Viber и E-mail; «Другое» и «Не определён» остаются отдельными категориями. Сохранённые ниже исторические замеры относятся к прежней классификации. Исходные KPI/status ring/три metric режима сохранены; source переключатель работает по готовым агрегатам.
- Finance source фильтрует таблицы и CSV. Глобальные KPI, расходы и cash distribution сохраняют полный месяц. Денежный donut содержит архивные оплаты, хотя исходная таблица долгов/оплат показывает действующие заказы: это разные явно подписанные выборки. Режим источников и исходные диаграммы доступны переключателем.
- `source=NON_WEBSITE` — объединение всех кроме WEBSITE, включая UNKNOWN; `OTHER` — отдельная доказанная категория. Не смешивать их.
- source/period/currency, совместимые списочные фильтры и состояние диаграмм сохраняются через URL/history. Finance→конкретный Order передаёт source/currency/tab=finance, но не превращает месяц получения оплаты в фильтр создания заказа.
- Новых финансовых endpoints и расширения ролей нет. Новая source-проекция передаёт только нормализованную категорию, без дополнительных raw provider payloads.

Синтетические acceptance фикстуры изолированы в tests/e2e. Локальные визуальные скриншоты используют фактический неизменяемый read-only снимок и собранный web, не production-установку нового API.

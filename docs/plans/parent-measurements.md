Дата: 19.10.2026. Статус: **оба этапа реализованы локально; проверки и итоговый LOCAL ACCEPT пройдены; деплой не выполнялся и запрещён текущим поручением**.

Основание: `YO_CRM_Parent_Measurements_Codex_TZ_v2.md`, утверждённый PNG и оригиналы из ZIP.
Рабочая область: `codex/website-sales`, worktree `finance-approved-redesign/YO_crm`.

## 1. Подтверждённые требования и уточнение владельца

- Существующие Athlete, Measurement и OrderItemInstance остаются единственными
  рабочими сущностями спортсменки, подтверждённых мерок и физического изделия.
- Один клиент может представлять команду. Родитель — отдельный участник заполнения,
  а не новый сотрудник CRM и не автоматически новый Client.
- Несколько родителей используют одну ссылку заказа, но не видят друг друга.
  Список на публичном экране содержит только детей текущего участника.
- Одна спортсменка может иметь один снимок для нескольких явно выбранных изделий;
  разные дети одного дизайна имеют отдельные экземпляры и снимки.
- Только m1, m2, m3, m15 обязательны; остальные 13 отсутствуют, если не заполнены.
  Рост — отдельное необязательное поле, не замена m1 и не пятая обязательная мерка.
- **Решение владельца 19.10.2026: m6 — чистая длина рукава без прибавки.**
  Менеджер явно видит «№6: без припуска; прибавку учитывать отдельно».
  Старые снимки/таблица с «+2 см» сохраняют своё значение. Автоматического ±2 нет.
- Весь интерфейс CRM сохраняет вкладку «Измерения» и таблицу из 17 параметров.
  Родительское подтверждение означает «Получено», а не «Проверено менеджером».

Проверены DTO, сервисы, основные потребители мерок, существующие тесты,
17-параметрическая схема и пять файлов инструкций. В ZIP используются фотографии
манекена для m1/m2/m3/m15 и оригинальная фирменная схема. Фото m15 показывает спину,
поэтому полный маршрут через пах и обратно к основанию шеи описывается текстом.
Исходная схема содержит «+2 см» для m6: её не ретушируем, рядом показываем явное
исключение для данной формы. Переведённые инструкции следуют той же семантике.

## 3. Модуль и границы доступа

Один Nest-модуль ParentMeasurements в текущем монолите: staff-контроллер
приглашений/проверки и public-контроллер личного заполнения. Общие проверки и
определения мерок остаются узкими TypeScript-модулями; не создавать отсутствующий
packages/shared или общий framework ради этой функции.

Staff: создание/отзыв приглашений и проверка через существующие роли OWNER,
ADMIN, MANAGER. Public: старт, своя сессия, свои дети/черновики, сохранение,
подтверждение, квитанция и восстановление. Каждая операция проверяет всю цепочку
credential → participant → invitation → order, срок, отзыв, владельца и архивность.
Любые clientId/orderId/athleteId из публичного тела не являются полномочиями.
Идентификатор вложенного объекта всегда проверяется вместе с participantId.

**Общая ссылка даёт только создание личной сессии.** Не возвращать общий список,
историю спортсменок, телефон, адрес, оплату, цены, контакты заказчика или другие заказы.
Начальный экран показывает бренд и безопасную ссылочную метку/номер заказа.
Новые спортсменки принадлежат текущему Client заказа, даже если это тренер.

Повторный заказ: менеджер после отдельной проверки представительства может связать
личного ребёнка с существующей Athlete. В первой версии публичного поиска по имени,
дате рождения и истории нет; повторное использование профиля выполняется менеджером.
Согласие родителя — декларация полномочий, не доказанная идентификация.

## 4. Предлагаемые изменения БД

Все новые бизнес-FK — RESTRICT, без каскадного удаления истории. Нет backfill,
переименования, пересчёта или обновления старых Measurement. CHECK/partial indexes,
которые Prisma не выражает, описать в новой проверяемой SQL-миграции.

| Таблица / поле | Назначение и основные ограничения |
| --- | --- |
| MeasurementInvitation | orderId, immutable clientIdAtIssue, createdById, tokenHash UNIQUE, SHARED/PERSONAL, expiresAt/revokedAt, admission limit/count, родительская shared-ссылка при перевыпуске для передачи. Несколько приглашений на заказ разрешены. |
| MeasurementParticipant | invitationId, locale, units, expiry/revocation, версия и время принятия уведомления/декларации; отдельная приватная область каждого родителя. |
| MeasurementParticipantCredential | participantId, SESSION/RECOVERY, tokenHash UNIQUE, generation, expiry, consumedAt/revokedAt. Один активный одноразовый recovery через partial UNIQUE; секреты не сохраняются. |
| MeasurementParticipantChild | participantId, стабильный child ID, draftRevision, draftSchemaVersion, ограниченный черновик профиля/значений/предложенного спорта, athleteId только после серверной проверки. UNIQUE(id, participantId); имя не является ключом. |
| MeasurementSubmission | childId+participantId scoped FK, revision, requestHash, operationKey, measurementId UNIQUE, athleteId, previousSubmissionId, неизменяемые подтверждения/предупреждения, submittedAt, отдельные reviewStatus и assignmentStatus. UNIQUE(participantId, operationKey) и UNIQUE(childId, revision). |
| MeasurementSubmissionTarget | Неизменяемое свидетельство конкретного назначения: submissionId, instanceId, before/after measurement IDs, actor/provenance, version, time. Это история событий, не второй источник текущей привязки. Текущая связь всегда OrderItemInstance.measurementId; последующие staff-операции не делают свидетельство «активной связью». |
| MeasurementPublicEvent | Append-only событие приглашения/участника/проверки; staffActorId только для STAFF, публичный actor — внутренний participant ID. Связь с AuditLog и requestId; без токенов и дублирования полного тела мерок. |
| MeasurementDraftAsset | Только если родитель добавляет необязательное фото ребёнка: private storage key, childId/participantId, MIME/size/hash, lifecycle. Авторизация каждого чтения, отсутствие public URL; фото не становится изображением дизайна. |
| Measurement.definitionVersion nullable | Новые родительские снимки получают server-owned PARENT_BODY_V1; NULL означает прежнюю семантику. Отдельное поле сохраняет numeric-only values JSON. Неизвестную версию нельзя молча интерпретировать как старую. |

assignmentStatus — вычисляемый API-статус по текущим instance.measurementId,
не независимый сохраняемый источник правды и не вывод из исторических Target events.
reviewStatus хранится отдельно и не означает наличия текущего назначения.

Нужны индексы invitation(orderId, createdAt), participant(invitationId),
child(participantId, updatedAt), submission(childId, submittedAt), events(scope, createdAt).
Связность order/client/athlete/instance проверяется повторно внутри транзакции;
одного FK существования недостаточно. previousSubmission относится к тому же child.
Для staff review/rebind — scoped операция с ключом+хешем и аудитом, без повторного
применения старого результата при сетевом retry.

Новый nullable definitionVersion требует совместимых читателей и writers:
клиент, Inbox, редактор/просмотр мерок, назначения/история экземпляра, копирование
новой версии и communication context. Копия наследует определение по проверенному
sourceMeasurementId; публичный boolean не управляет семантикой. Редактирование
всегда создаёт снимок. Из старого снимка в родительский m6 не переносится автоматически.
Старый preset m6 исключить также из поиска ближайшего размера родительской формы.

## 5. Предлагаемая политика безопасности для согласования

1. Независимые CSPRNG-секреты по 32 байта; хранить только purpose-separated hash.
   URL вида /parent-measurements#invite=…; очистить fragment до прочих запросов.
   Явный POST-обмен, GET/preview не создаёт участника и не расходует recovery.
2. Отдельная HttpOnly/Secure/host-only cookie с SameSite=Lax и ограниченным path
   публичного API; отдельный session-bound CSRF token, точный Origin, Fetch Metadata,
   JSON-only mutations. Не менять staff-cookie и не путать cookie path с авторизацией.
3. no-store для HTML/RSC/API/ошибок/файлов, no-referrer, noindex, проверенный CSP.
   Без аналитики, session replay, внешних виджетов и сторонних загрузок фотографий.
   Публичный layout не получает CRM-данные; локаль/RTL и стили ограничены его деревом.
4. Предложение сроков: приглашение 14 дней; participant не дольше приглашения;
   session 7 дней с верхним пределом приглашения; одноразовый recovery 24 часа.
   PERSONAL допускает одного участника; SHARED по умолчанию до 100; до 10 детей
   у участника. Лимиты настраиваемы менеджером в разрешённых пределах.
5. Отзыв приглашения сразу закрывает дочерние сессии/recovery. Ротация отзывает
   старую цепочку; новые ссылки не восстанавливают старые доступы автоматически.
   На закрытом/архивном заказе новые приглашения и записи запрещены, история CRM
   сохраняется. Архивирование/merge/split отзывает доступ; повторная активация только
   новым проверенным приглашением. Split с новыми зависимостями требует их явного
   распределения менеджером или отклоняется без частичного изменения данных.
6. Hash-only означает, что старый секрет нельзя получить повторным GET из БД.
   Copy/QR доступны при выдаче. После перезагрузки сотрудник создаёт дополнительное
   приглашение либо явно отзывает/заменяет старое. Для «Поделиться» участник SHARED
   получает новое ограниченное приглашение той же корневой области, с общими квотами,
   сроком не дольше исходного и наследованием отзыва. PERSONAL не расширяется до SHARED.
   Личная recovery-ссылка никогда не попадает в «Поделиться».
7. Восстановление: приватная одноразовая ссылка выдаётся по явной кнопке, raw secret
   показывается один раз. POST consume атомарно меняет generation и отзывает старые
   credentials; повторное использование запрещено. При потере ссылки/ответа обмена
   помогает менеджер после проверки, общая ссылка не ищет старого ребёнка.
8. Redis-лимиты до lookup и на участника/приглашение, квоты изображений, body limit
   32 KiB для JSON до общего parser, ограниченные строки/массивы. Начальные бюджеты:
   start 10/IP/10 мин, draft 120/participant/10 мин, submit 10/час, recovery 5/IP/15 мин.
   Invalid-token ключи не создают неограниченную кардинальность. Redis outage:
   обмен/записи/recovery закрыты с понятным retry; не выдавать ложное «Сохранено».
9. Логи не содержат секреты/cookies/CSRF/тела/имена/мерки. До публичного запуска
   проверить настоящую цепочку NPM → Next → API, доверенные proxy hops, подмену XFF,
   прямые порты и логи. Изменения инфраструктуры отдельно согласуются.
10. Предложение retention: незавершённые черновики/неиспользованные фото удаляются
    через 30 дней после прекращения доступа; подтверждённые снимки — по действующей
    политике истории CRM. Требования на исправление/удаление обрабатывает менеджер
    с учётом связанной истории; автоматическое стирание подтверждённых версий не обещаем.
    Назначение сбора, контакт и versioned consent показываются до ввода.

Для повторного входа после закрытия браузера используется серверный черновик и
cookie. При потере сети несохранённые изменения остаются в открытой форме, виден
статус и повторная отправка. Не кэшировать персональные данные service worker или
plaintext localStorage. Закрытие вкладки до подтверждённого серверного сохранения
может потерять последнюю несохранённую правку: предупреждение явно показывается.
Долговременное полностью офлайн-хранение — отдельное решение, не скрытое обещание.

Основа защиты: [OWASP session management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html),
[CSRF prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html),
[одноразовые recovery-секреты](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).
Это проект мер защиты, не утверждение о пройденном live security-аудите.

## 6. Подтверждение, назначения и конкурентность

Один submit = одна транзакция: существующий merge-global/order/client lock protocol,
повторная проверка доступа/владельца, блокировка child/revision, идемпотентность,
обычная Athlete (если не создана), новый Measurement, Submission, Activity/Audit.
Все новые операции используют согласованный порядок блокировок, включая отзыв.
Повтор того же ключа и тела возвращает исходную квитанцию, другое тело — conflict.
Разные ключи одной ревизии не создают два снимка. Новая явная коррекция — новая версия.

По умолчанию SHARED сохраняет **Получено / Ожидает назначения**. Единственный
оставшийся свободный костюм не доказывает принадлежность ребёнку. Автоназначение
разрешено только на заранее проверенный менеджером конкретный child/athlete/target
binding, после проверки owner, archive, eligibility и expectedUpdatedAt каждого ID.
При неоднозначности на preflight получаем снимок без назначения и причину менеджеру.
При CAS-конфликте после начала записи — полный rollback, затем явный retry/review;
не коммитить частично назначенную группу или orphan snapshot.

Менеджер назначает один снимок нескольким изделиям только явным выбором.
Переназначение начатого производства требует отдельного version-bound подтверждения
и причины; готовое, завершённое, отменённое или отправленное изделие остаётся закрытым.
Ничего автоматически не меняет количество, деньги, скидку, статусы заказа,
производственные слоты/даты, спорт дизайна или старые корневые/item-ссылки.
Спорт родителя, отличный от дизайна, сохраняется предложением для менеджера.

## 7. Мобильная форма и точность данных

- Визуальные ориентиры PNG: белый/фиолетовый, компактные карточки, progress,
  пошаговые фото, нижние действия. Mantine и существующие токены; собственные только
  доменные компоненты. Публичный roster ограничен своим participant.
- RU/EN/FR/DE/ES/IT; auto detect + ручная смена без потери данных. Подготовить
  структуру остальных локалей из ТЗ и RTL. Старые русские staff-подписи централизованы.
- Исходные 17 номеров сохраняются. Фото оригинальные, optional child photo не требуется;
  инициалы работают без загрузки. Не требовать дату рождения вместо необязательного возраста.
- Канонические значения — целые полусантиметры; cm = ticks/2, inch = cm/2.54.
  Переключение единиц не парсит заново округлённый display. Ручной inch-ввод показывает
  результат округления до 0.5 cm и требует подтверждения, если значение изменилось.
- Предустановки 17 ростовых размеров действующей таблицы: только явная кнопка и
  заполнение пустых допустимо сопоставленных полей. m6 legacy не подставляется.
- Slider и число синхронны на решётке 0.5 cm. Только при утверждённом диапазоне [L,U]
  slider имеет [L−3,U+3]. Номинальные размеры не являются доказанными нормами.
  Пока ателье не предоставило диапазоны, поле работает числом без выдуманных предупреждений.
  Выход за мягкую норму разрешён после «Проверено, верно», подтверждение видит менеджер.
- measuredAt — выбранная родителем дата измерения; submittedAt — серверное время.
  Невалидная/будущая дата отклоняется; timezone явно согласован с business date CRM.
- Autosave с debounce, revision/CAS, запретом позднему ответу перезаписать новые поля,
  состояниями сохранения/ошибки/сети. Back, язык, единицы и переходы данные не сбрасывают.
- Итог показывает 4 обязательные + N/13 дополнительных, дату, предупреждения и согласие.
  Успех подтверждает получение, не проверку ателье. Все CRM-обновления асинхронны.
- «Отправить в переписку» вставляет текст/ссылку в черновик Inbox, не отправляет сообщение.

## 8. Два этапа реализации после согласования

**Этап 1 — защищённый сквозной сценарий.** Новая SQL-миграция на изолированной БД,
domain/guards/DTO, приглашения/личные сессии/recovery, autosave/submit, immutable
snapshots, очередь менеджера, явные назначения, m6-compatible readers/writers,
merge/split защита, минимальный рабочий public UI. Проверить 3 независимых родителей
одного заказа до детальной визуальной отделки. Ни одного production-действия.

**Этап 2 — полный мобильный интерфейс.** Все шаги утверждённого PNG, шесть языков,

Перед изменением кода зафиксировать манифест существующего dirty baseline. Объём

автоматического commit/push/issue creation. Исходный PNG/фотографии использовать
без генерации новых изображений; приватный manifest уже фиксирует SHA256 оригиналов.

## 9. Проверки, миграции и выпуск

Red-first сценарии на существующих швах assignments/immutable measurements и новом
HTTP-модуле. Реальный изолированный PostgreSQL нужен для race/lock/CAS, не только mocks.

| Область | Обязательная проверка |
| --- | --- |
| Приватность | Три browser contexts, один invite, чужие child/submission/file IDs на всех verbs; отсутствие доступа к staff и истории по общей ссылке. |
| Жизненный цикл | Expiry/revoke/rotation/recovery replay, personal admission race, потеря ответа, CSRF, cookie flags, invalid token uniformity, Redis down, body limits, safe logs. |
| Атомарность | submit×submit, edit×submit, revoke×submit, archive/merge/split×submit, target CAS, audit failure, lost response retry, одна ревизия → один Measurement. |
| Бизнес-связи | Один дизайн/несколько детей, несколько дизайнов/один ребёнок; общая ссылка без guessed assignment; started/ready/shipped ограничения; quantity/finance/slots неизменны. |
| Семантика | Legacy и PARENT_BODY_V1 с одинаковым m6 отображаются различно; copy/edit/history/Inbox/context сохраняют определение; неизвестная версия не переосмысливается. |
| Форма | 4 required, 13 optional, все 17 номеров, m15 маршрут, cm/in без дрейфа, локальные числа, half-cm slider, без overwrite preset, soft warning confirmation, reload/server resume. |
| Совместимость | Старые клиент/заказ/Inbox/KeyCRM/платежи/производство; staff RBAC и hooks; миграция на копии схемы без изменения старых строк. |
| UI | Все шесть языков, мобильные размеры, desktop, клавиатура/a11y, длинные строки, отсутствие reload, actual screenshots + визуальный отчёт. |

После реализации: pnpm typecheck/test/build/quality:check, затронутые e2e и пять
обязательных независимых ролей .agents/README.md, затем release gate без blockers.
При планировании эти команды не запускались и зелёная реализация не заявляется.

Миграция только добавляет таблицы/индексы и nullable definitionVersion. Отдельно
проверить SQL, FK/checks и блокировки на локальном PostgreSQL. Не выполнять db push,
reset, seed или запуск production Compose (его startup может выполнять migration/seed).

Откат после первых родительских данных: отключить новые приглашения/submit,
сохранить таблицы/снимки/аудит и использовать только версию приложения, понимающую
definitionVersion. Старое приложение, показывающее m6 как «+2», небезопасно для отката.
Не удалять новые таблицы и не восстанавливать старую БД поверх принятой истории.

Публичный запуск остаётся отдельным согласованием: FULL backup, проверка установленной
сети/логов, утверждённый privacy text/контакт, квоты/retention, migration/release review,
live smoke после разрешённого выпуска. Текущее согласование плана этого не разрешает.

## 10. Что именно предлагается согласовать сейчас

Два независимых read-only аудита плана (security/compatibility и интеграция
измерений/экземпляров) не нашли блокирующих противоречий в итоговом плане.
Их PASS условен на согласование владельцем и не заменяет приёмку реализации.

Локальную реализацию двух этапов, перечисленную additive-модель БД и защиту
публичных ссылок; m6 без прибавки с versioned provenance; общий invite без доступа
к истории и с назначением менеджером; сроки/квоты/retention как предложено выше;
отзыв при смене владельца, закрытом заказе или ротации; отсутствие автоматической
отправки клиентам и production-действий. Допустимые измерительные диапазоны должны
быть предоставлены ателье: их отсутствие не блокирует числовой ввод и не оправдывает
выдуманные нормы. Публикация privacy text проверяется отдельно перед запуском.

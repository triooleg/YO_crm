## Поведение

- Панель родителей располагается внутри существующего блока «Измерения», а не
  отдельной длинной таблицей перед ним. Остаются спортсменки, основные мерки,
  использование в изделиях и история. Управление ссылками и подробности доступны
  через компактные элементы Mantine; длинный список не растягивает весь заказ.
- Для полученной анкеты по умолчанию достаточно имени, состояния и четырёх
  основных мерок. Все 17 значений доступны явно, в ограниченной по высоте области.
  Проверка, уточнение, назначение, защита производства, CAS и повтор запросов
  сохраняют прежнее поведение. Закрытие интерфейса не теряет неизвестный результат
  операции или только что выданную одноразово показываемую ссылку.
- В родительской форме числовое поле узкое, примерно до двойной ширины текста;
  единица измерения рядом, ползунок в той же строке. Ползунок доступен и без нормы:
  его диапазон служит удобству ввода, а не проверке телосложения. Не подставлять
  пустое значение автоматически, не обрезать ранее введённое число, сохранить
  шаг 0.5 см, перевод дюймов и явное согласование округления.
- В инструкции en используется приложенная английская схема, fr — французская.
  Фотоподсказки остаются. Увеличение показывает выбранную схему. Подпись мерки №6
  в форме сохраняет согласованное правило чистой длины без +2 см, независимо от
  старой подписи в оригинальном изображении.

## Уточнение 19.10: новый обязательный эталон вкладки CRM

Источник: D:/download/YO_CRM_Measurements_Tab_Codex_TZ.md и соответствующий Approved_Design.png. Последнее уточнение заменяет прежнюю компоновку staff-панели. Публичная форма сохраняет отдельные ползунки/схемы; внутри CRM их нет.

### Инвентаризация перед реализацией

- Staff GET /orders/:orderId/parent-measurements: приглашения, отправки с конечными values, notes, warnings, immutable measurementId/athleteId, независимые reviewStatus/assignmentStatus, черновики и спортсменки клиента.
- POST invitations / invitations/:id/revoke; POST submissions/:id/review /assign; POST children/:id/bind. Защищённое фото GET submissions/:id/photo. Существующие guards OWNER/ADMIN/MANAGER, CAS и аудит сохраняются.
- Public session/children/save/submit/revise/recovery/share/photos остаются без изменений контрактов; приватность общей ссылки принадлежит существующему participant-контексту.
- Клиентские athletes и POST athletes/:id/measurements создают неизменяемые версии. sourceMeasurementId сохраняет семантику исходного определения. Назначение физическому экземпляру — существующие order-tabs instances и WIP/CAS подтверждение.
- OrderNote уже поддерживает athleteId, category MEASUREMENTS, visibility INTERNAL, автора, revisions, updatedAt CAS и аудит. Комментарий администратора сохраняется здесь отдельно от родительского notes; новая таблица не нужна.
- Parent submission.payload уже содержит исходные возраст, язык/единицы и фотографию. Dashboard дополнится безопасной provenance-проекцией из неизменяемого payload и submittedAt; не из изменяемого child.draft. Токены/контакты/секреты не возвращаются.
- Read-only отправленная форма — авторизованный диалог имеющихся данных dashboard, без публичной ссылки и без инструкций. Непредоставленные метаданные отображаются как неизвестные.

### Реализация

Компактный toolbar; три адаптивные колонки 22/60/18; четыре обязательные карточки; раскрываемая сетка остальных 13; история и администраторский комментарий снизу. Подлинные фотографии только по существующему защищённому endpoint. Изменение — новая версия с датой, комментарием и сравнением значений; отсутствие значения не становится нулём. Ручной ввод использует существующий Drawer и сохраняет серверные проверки принадлежности и назначения. Цены/производство/доставка не затрагиваются.

Миграции схемы не требуются. Production, публикация диапазонов, Git commit/push и deploy не выполняются. Проверки включают все сценарии нового ТЗ и desktop 1920/1703/1366, tablet/mobile. Сравнение ведётся с новым PNG, не с предыдущей длинной таблицей.

### Дополнение: повтор ручного сохранения после потерянного ответа

Используем уже существующие идемпотентные POST /order-tabs/:orderId/athletes и /order-tabs/:orderId/athletes/:athleteId/measurements. Не меняем ClientsService/DTO/схему. Order-owned путь уже проверяет ключ операции, hash, действующий профиль, источник версии и сохраняет аудит в одной транзакции. UI удерживает operationKey для точного неизменившегося запроса и выбранную/созданную спортсменку при повторе. Старые client-only consumers остаются на своих маршрутах без нового поля. Назначение экземпляру сохраняет отдельный CAS/WIP-контракт. Предыдущая идея расширить клиентский API отброшена до изменения backend: нужный контракт уже существует.

### Закрытие замечаний приёмки

Для существующей спортсменки ручной редактор получит действующий справочник видов спорта и отдельное подтверждение отличия от спорта дизайна. Сохранение профиля использует существующий PATCH athlete с необязательной парой discipline/expectedDiscipline: имя-only consumers неизменны, ownership/locks/CAS/audit сохраняются. Изменение касается профиля спортсменки, не дизайнов, полученных submission или прошлых snapshot. Нужны red-first проверки пары/enum/конфликта/повтора; миграций нет. Новая спортсменка проходит тот же существующий wizard с опциональным правым Drawer и отдельными датой/комментарием снимка. Эти параметры включены только во вкладке заказа.

План возврата разрешает старые образы только до новых бизнес-изменений, при полном совпадении исходного снимка и отсутствии новых операций/архивных полей; после изменений допустим только совместимый roll-forward. Ни возврат на старые образы, ни restore/down-migration не выполнялись.

## Рабочий сайт и ограничения

HTTPS root и `/api/health` с клиентского хоста вернули точные HTTP200, health `ok=true`. Самозапрос публичного домена с сервера получил timeout; этот транспортный сбой сохранён отдельно и не выдан за PASS. Браузерные проверки выполнялись через настоящий публичный HTTPS с действительной авторизацией.

Первые реальные проверки дали 18 PASS, затем выборка с настоящими назначенными мерками — 25 PASS, без ошибок console/runtime/network, заблокированных чтений и попыток запрещённой записи. Разрешены только login/logout и неизменяющий состав preview; никаких apply/archive/assign/payment/provider/import действий в рабочей системе. Проверены API/UI Finance KPI, Overview, девять вкладок, ID физических экземпляров, 17 значений мерок и прямой/обратный переход по реальному usage. Исторической/архивной строки в ограниченной выборке не оказалось — UNAVAILABLE; данные не создавались ради теста. Пустое историческое покрытие не заменяет отдельные локальные и реальный PG тесты.

После запуска строгая сверка обнаружила различие Order/Activity/AuditLog; исходный неуспешный журнал сохранён. Ограниченная проверка READ ONLY / REPEATABLE READ доказала: 8 заказов изменили **только salesStatus и updatedAt**, существуют ровно 8 новых событий Activity и 8 AuditLog, текущие строки совпадают с последним Audit.after. Исходные строки всех трёх таблиц точно реконструированы через первые Audit.before/исходную историю: count и hash совпали с неизменяемым снимком перед миграцией. Остальные **19 таблиц побайтно по полям/количествам неизменны**, включая Payment, Invoice, Expense, Measurement, Athlete, OrderItem/Instance и производственные/доставочные связи. Удалений и других изменений в проверенном объёме не обнаружено.

Проверка pairing сначала ошибочно требовала одинаковый createdAt двух последовательных INSERT; фактический разрыв Activity→Audit составил 2–11 мс. Исправлен только приватный проверяющий helper: направление, предел 100 мс, одинаковые order/status/client, уникальная пара в обе стороны; все исходные контрольные суммы и остальные guards сохранены. Actor/источник/причина запросов не атрибутируются. Проверочный браузер не выполнял PATCH/apply. Никакие данные не исправлялись, не откатывались и не перебазировались ради PASS.

# YO CRM — техническое задание для Codex: «Статистика продаж»

**Репозиторий:** https://github.com/triooleg/YO_crm  
**Базовый раздел:** `/?section=overview`  
**Утверждённый визуальный эталон:** `YO_CRM_Sales_Statistics_Approved_Design.png`  
**Цель:** создать полноценный аналитический режим для анализа заказов, костюмов, стран, источников, клиентов и финансов, не разрушая существующую оперативную главную страницу.

## 1. Обязательные правила

1. Приложенный PNG — согласованный визуальный эталон: соблюдать расположение, размеры и иерархию блоков, фирменный фиолетовый стиль, типографику, скругления, отступы, таблицы, легенды и диаграммы. Не предлагать альтернативный дизайн.
2. Числа, страны, клиенты и суммы на изображении **демонстрационные**. Все значения в production — исключительно из реальной базы YO CRM.
3. Не переписывать действующие модули заказов, клиентов, платежей и доставки. Использовать существующие API/сервисы, расширять агрегирующие read-only endpoints по необходимости.
4. Сохранить раздел «Обзор» без изменения его оперативных блоков, задач, отправок, сообщений и предупреждений. Добавить в него переключение **«Обзор» / «Статистика»**. Статистика — самостоятельное представление с глубокими ссылками, отдельными loading/error/empty состояниями.
5. Перед началом прочитать `AGENTS.md`, `apps/web/AGENTS.md`, `.agents/README.md`, архитектурные документы, актуальную схему Prisma, реальные API, существующие KPI и тесты. Не считать имена файлов/маршрутов из ТЗ доказательством их актуальности — проверить репозиторий.
6. Не запускать деплой, миграции production, массовые исправления исторических записей или финансовых данных без отдельного разрешения.

## 2. Навигация и верхняя панель

Под общим header YO CRM: заголовок «Статистика продаж», подзаголовок, переключатель «Обзор / Статистика», глобальный период, две стрелки перехода по периодам, выбор валюты EUR/USD/UAH и «Экспорт». Переходы между режимами не должны терять выбранный период без необходимости.

Под KPI: вкладки аналитики **«Страны», «Источники», «Клиенты», «Виды спорта», «Типы заказов»**. Ниже фильтры по источнику, статусу, клиенту, стране, типу заказа и периоду, кнопки «Применить» и «Сбросить». Использовать серверные фильтры с URL/deep-link state, back/forward и reload. При адаптивности сохранять доступность всех фильтров.

## 3. Верхние шесть KPI

Расположить шесть карточек в одну строку на широком экране, адаптивно на узком:

1. **Всего заказов** — число заказов, созданных в выбранном периоде.
2. **Всего костюмов** — сумма физических экземпляров изделий, а не количество дизайнов; корректно учитывать `quantity` и новую модель экземпляров без двойного счёта.
3. **Стран покупателей** — число уникальных нормализованных стран доставки; неизвестные страны отдельно.
4. **Уникальных клиентов** — distinct канонических клиентов с заказами периода, без дублирования после объединения профилей.
5. **Повторные покупки** — количество повторных заказов и доля повторных клиентов с чёткой формулой в tooltip. Определить первый заказ клиента по всей доступной истории, а не только по выбранному периоду.
6. **Сумма заказов** — стоимость заказов периода в выбранной валюте, отдельно от фактически полученных платежей; явно обозначить включение/исключение доставки, скидок, отмен и возвратов.

Для KPI сравнение с аналогичным предыдущим периодом: разница и процент при ненулевой базе, «—» при отсутствии базы. Все карточки кликабельны: открывают соответствующий список с фильтрами или аналитический drill-down.

## 4. Первый ряд аналитики

### 4.1 География продаж

Интерактивная карта мира в левой карточке. Страны закрашены по количеству заказов; легенда диапазонов, hover с названием страны, числом заказов, количеством костюмов, суммой заказов, средним чеком и уникальными клиентами. По клику — отфильтрованный список заказов этой страны. Кнопки масштаба и корректная мобильная альтернатива списком.

Географию определять прежде всего по **стране доставки конкретного заказа**, а не по стране Instagram-аккаунта или телефонному коду. Если страна доставки неизвестна, отдельно показывать «Не определена»; не подставлять страну клиента молча. Нормализовать ISO country codes и альтернативные названия.

### 4.2 Динамика заказов по странам

Stacked bar за последние 6 месяцев по умолчанию (выбор 3/6/12 месяцев). ТОП-5 стран по количеству заказов за период + «Остальные». Каждая часть столбца кликабельна и ведёт в заказы с выбранными страной и месяцем. Tooltip: число заказов, число костюмов, сумма. Возможность переключить метрику «Заказы / Костюмы / Сумма» при сохранении общей компоновки.

### 4.3 Заказы по источникам

Donut с числом заказов, процентами и легендой. Категории на основании **источника оформления заказа**, не способа оплаты и не канала последующей переписки: «С сайта», Instagram, WhatsApp, Ручной/CRM, Facebook, Viber, E-mail, другие, «Не определён». Клик по сектору/легенде — список заказов с фильтром. Не классифицировать KeyCRM-импорт как «с сайта» без подтверждённого признака.

## 5. Второй ряд

### 5.1 ТОП-10 стран по заказам

Таблица: место, флаг и страна, заказы, костюмы, сумма заказов, средний чек. Сортировка по любой числовой колонке, «Все страны», переход к заказам по стране. Обозначить валюту. Показать отдельно неопределённую страну при наличии таких заказов.

### 5.2 ТОП-10 клиентов по сумме заказов

Таблица: место, клиент, страна, количество заказов, количество костюмов, сумма заказов. По клику открыть карточку клиента или его заказы. Добавить переключатель ранжирования «Сумма заказов / Получено платежей / Число заказов / Костюмы». Не путать заказы и реальные поступления, не раскрывать финансовые данные ролям без доступа. Объединённые клиенты не должны дублироваться.

### 5.3 Новые и постоянные клиенты

Stacked bar по месяцам: новые клиенты (первый в истории заказ приходится на месяц) и постоянные (имеют предыдущий заказ). Переключение «Количество клиентов / Количество заказов». Клиент, совершивший несколько заказов за месяц, учитывается один раз в метрике уникальных клиентов. Подсказка с методикой расчёта.

## 6. Третий ряд

### 6.1 Распределение заказов по видам спорта

Donut: художественная гимнастика, спортивная акробатика, фигурное катание, спортивная аэробика, твирлинг и другие реально поддерживаемые дисциплины. Неизвестные — отдельная категория. Если один заказ содержит несколько дисциплин, при метрике «Заказы» не удваивать итог: либо считать distinct заказов по каждой дисциплине с явной оговоркой о пересечениях, либо использовать отдельную метрику **костюмов по видам спорта** (предпочтительно для взаимоисключающих секторов). Tooltip и клик — фильтр.

### 6.2 Динамика выручки

Столбчатая диаграмма по месяцам, выбор периода. Явно назвать метрику: «Стоимость созданных заказов» или «Фактические поступления». Предусмотреть переключение этих метрик. Для заказов группировка по `createdAt`, для платежей — по фактической дате получения. Учитывать void/refund по существующей политике.

### 6.3 Средний чек по источникам

Горизонтальные полосы для источников заказов, сумма среднего чека и сортировка. Средний чек = общая стоимость подходящих заказов / количество подходящих заказов (при ненулевом знаменателе). Не использовать среднюю цену костюма вместо среднего чека заказа. Клик — фильтр заказов по источнику.

## 7. Дополнительные вкладки аналитики

Все пять вкладок в панели должны иметь полезные данные, а не быть декоративными:

- **Страны:** карта, ТОП стран, помесячная динамика, заказы и клиенты по странам.
- **Источники:** доли каналов, динамика, средний чек, поступления, конверсия только при наличии достоверных данных о лидах (иначе не показывать).
- **Клиенты:** ТОП клиентов, новые/повторные, частота заказов, lifetime value как сумма заказов и отдельно фактических платежей.
- **Виды спорта:** распределение изделий, количество заказов, средняя цена изделия, динамика по дисциплинам.
- **Типы заказов:** индивидуальные, пары, трио, групповые и другие реально существующие категории; число заказов, число костюмов, средний размер заказа и суммы. Не угадывать тип по имени клиента.

Можно сохранять общую шапку и KPI, а нижние блоки адаптировать под вкладку, сохраняя дизайн PNG. При переключении вкладок фильтры должны быть согласованными.

## 8. Валюты и финансовая достоверность

Валюта EUR/USD/UAH влияет на **все денежные показатели**, таблицы, tooltips, графики и экспорт. Исходные суммы/валюты не переписывать. Использовать существующую политику FX и округления; если исторический курс отсутствует, показать предупреждение/неполные данные, не придумывать курс. Нельзя суммировать разные валюты без приведения.

Отдельно различать: стоимость заказов, поступившие платежи, задолженность и финансовый результат. Учитывать реальные скидки, доставку, возвраты, отмены, архивы и частичные оплаты согласно согласованной политике. В интерфейсе дать пояснения к формулам.

## 9. Данные, производительность, безопасность

Использовать серверную агрегацию по всему набору, а не только видимым 20 строкам. Предпочитать общие сервисы нормализации стран, источников, валют и заказов. Не создавать отдельную противоречащую бизнес-логику на фронтенде. Кэшировать тяжёлые отчёты с понятным TTL и обновлением; избегать N+1. Сохранять RBAC, audit, обработку ошибок, пустые состояния, защиту персональных данных. Экспорт CSV/XLSX — с теми же фильтрами, валютой и семантикой, что и экран.

## 10. Кликабельность и навигация

Обязательно проверить: KPI → список; страна на карте/в таблице → заказы по стране; сектор источника → заказы по источнику; столбец месяца → заказы за месяц; клиент → профиль клиента; дисциплина → заказы/изделия; «Все страны» и «Все клиенты» → полные соответствующие списки. Использовать реальный роутер CRM, сохранить фильтры в URL или штатном navigation state. Browser Back/Forward, reload и deep links должны работать. Не делать декоративные ссылки без обработчика.

## 11. Визуальная приёмка

Основной ориентир — приложенный PNG. Сравнить скриншоты при 1536×1024 и 1920×1080, дополнительно 1366×768, планшет и мобильный. Проверить шесть KPI, 3×3 карточки диаграмм/таблиц, верхние вкладки, легенды, типографику, отступы, фильтры и валюту. Сохранить верхнюю навигацию и стили других разделов YO CRM. На мобильном использовать вертикальную компоновку и доступные таблицы.

## 12. Тесты и сценарии

1. Один заказ с 6 костюмами = 1 заказ, 6 костюмов.
2. Один заказ с несколькими дизайнами/видами спорта — без двойного подсчёта заказов.
3. Заказ из Франции с клиентом из другой страны — география по адресу доставки.
4. Заказ с сайта, затем общение в Instagram — источник остаётся «С сайта».
5. KeyCRM-импорт без достоверного источника — «Не определён».
6. Повторные заказы одного клиента в одном месяце — корректный distinct и repeat.
7. Сентябрьский заказ с октябрьской оплатой — разная дата в соответствующих графиках.
8. Смена EUR/USD/UAH, отсутствие курса, частичные оплаты, отмены, возвраты.
9. Фильтры, сортировки, drill-down, reload, back/forward, экспорт.
10. Нет утечки финансовых данных при ограниченных ролях.
11. Данные на графиках согласованы с таблицами и общими KPI.
12. Нет регрессий существующей стартовой страницы «Обзор».

Запустить релевантные тесты, `pnpm typecheck`, `pnpm test`, `pnpm build`, `pnpm quality:check` и проверки из AGENTS.md. При несовпадении скриптов с текущим репозиторием использовать актуальные и объяснить замену.

## 13. Этапы и результат

1. Аудит моделей, источников, стран, клиентов, FX и API; предложить точные формулы KPI.
2. Серверные read-only агрегаты и тесты.
3. UI режима «Статистика» по PNG, адаптивность.
4. Все пять аналитических вкладок и фильтры.
5. Переходы, экспорт, RBAC, визуальное сравнение и регрессия.

Предоставить список файлов, спецификацию формул, скриншоты, результаты тестов, ограничения исторических данных и список вопросов, требующих отдельного согласования. **Не выполнять деплой или рискованные production-миграции без отдельного разрешения владельца.**

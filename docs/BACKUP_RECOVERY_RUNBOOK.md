# Резервирование, проверка и перенос YO CRM

Этот регламент относится к расширению существующего BackupsModule. Его установка
на рабочем сервере, остановка рабочих writers, экспорт настоящих секретов,
удаление архивов и production cutover требуют отдельного разрешения владельца.
Не выполняйте команды ниже в production как часть ознакомления с документом.

## Архивы и внешние зависимости

DATA содержит полную CRM PostgreSQL и долговечные uploads. Новый согласованный
формат v3 содержит файловый inventory, таблицы/отпечатки и сведения о барьере
записи. FULL v3 дополнительно содержит приложение, миграции, Compose, инструкции
и сведения о точных образах/архитектуре. Offline-режим добавляет docker-save.
Legacy v1/v2 читаются, но не получают задним числом доказательство согласованности.

Архивы чувствительны: dump содержит персональные данные, staff password hashes,
историю и шифротекст интеграционных настроек. Обычный FULL не включает `.env`,
SETTINGS_ENCRYPTION_KEY, SECRET_KEY_BASE Chatwoot, TLS private keys или пароли
внешнего хранилища. Они сохраняются отдельно. Потеря исходного ключа шифрования
может сделать интеграционные настройки нечитаемыми после восстановления.

Chatwoot self-hosted имеет собственную БД, pgvector, media и секреты. Его захват
включается только после явной инвентаризации writers/томов/версий. Отметка
`chatwoot:false` означает, что оригинальная система Chatwoot не включена.
Импортированные сообщения CRM и внешние URL не заменяют её резервную копию.
Данные Gmail/Meta/других провайдеров за пределами локального импорта также
не объявляются сохранёнными. Redis считается восстанавливаемым cache.

## Работа владельца в CRM после одобренной установки

«Настройки → Резервное копирование» показывает архивы и отдельные результаты
целостности, restore drill и внешнего хранения. «Создать копию данных» и
«Создать полный пакет» ставят задание в существующий каталог Backup.
Без подключённого host agent заявка остаётся ожидающей, а интерфейс показывает
отсутствие исполнителя. Настройка расписания сама по себе не устанавливает agent.

«Скачать архив» требует текущий пароль и отдаёт проверенный файл приватным
потоком. Не передавайте пароль в URL. Временная схема владельца — сохранить
архив на рабочем компьютере и отдельно хранить необходимые ключи. Рекомендуется
зашифрованный диск/каталог и дополнительная независимая копия. Успешный download
не доказывает, что файл сохранился на другом устройстве или успешно восстанавливается.

«Загрузить архив» принимает один gzip/tar в карантин после повторной проверки
пароля. Лимит по умолчанию2GiB, с проверкой свободного места и квот ожидающих
импортов. Загруженный архив не изменяет CRM и не исполняет свой код. После
проверки доступны integrity/isolated drill. Непроверенный импорт не становится
доверенным только потому, что автор manifest написал `verified:true`.

## Отдельный host agent

Исполнитель работает вне web API. Никогда не монтируйте Docker socket в API.
Нужны Linux/Python3, Docker Compose и доступ только к разрешённому проекту и
приватному backup-каталогу. Учётная запись с Docker-доступом привилегированна;
не предоставляйте этот доступ web-пользователям или входящему API-токену.
Конфигурационный файл агента принадлежит deployment account, режим0600.

Пример **только после адаптации и отдельного разрешения**:

```json
{
  "project": "REVIEWED_PROJECT",
  "composeFile": "/ABS/reviewed-compose.yml",
  "envFile": "/PRIVATE/reviewed.env",
  "storageRoot": "/PRIVATE/backups",
  "repositoryRoot": "/ABS/verified-release",
  "consistent": true,
  "writerServices": ["api"],
  "writersComplete": true,
  "offlineImages": true,
  "allowAutomaticRetention": false,
  "postgresImage": "sha256:REVIEWED_INSTALLED_IMAGE_ID",
  "pollSeconds": 15
}
```

`writersComplete` — осознанная инвентаризация всех writers, а не способ обойти
проверку. Отдельные sender/import services должны быть перечислены тоже.
Разрешение паузы требуется одновременно в настройке CRM и host-конфигурации.
При пропаже lease/питания сохранённый журнал требует проверки ownership перед
возобновлением. Не удаляйте lock/journal, чтобы «запустить ещё раз».

Одноразовый запуск после одобрения: `python3 scripts/backup-agent.py --config
/PRIVATE/agent.json --once`. Постоянный процесс можно оформить отдельным systemd
unit с тем же файлом. Включать автозапуск до приёмки нельзя. Расписание читается
из существующих BackupSetting и AppSetting(backups,recovery); DATA/FULL/drill
исполняются тем же worker, с idempotency и единым execution fence.

## Изолированное восстановление

Используйте установленный доверенный `recovery-drill.py`, а не скрипт из
загруженного архива. Укажите новый project с префиксом `yo-recovery-`, новый
пустой приватный каталог и заранее проверенный PostgreSQL image ID:

```bash
python3 scripts/recovery-drill.py \
  --backup-dir /PRIVATE/backups/SELECTED_ID \
  --project yo-recovery-UNIQUE \
  --postgres-image sha256:REVIEWED_INSTALLED_IMAGE_ID \
  --output-dir /PRIVATE/drills/NEW_EMPTY_TARGET
```

Это новый изолированный PostgreSQL, без public ports, production volumes,
Docker socket и egress. Неверные checksums, traversal, symlink/hardlink,
спецфайлы, дубликаты и превышенные resource/expansion limits отклоняются.
Проверяются таблицы/бизнес-отпечатки, файловые SHA/размеры и известные локальные
ссылки. Неизвестные будущие JSON-контракты и remote URL отражаются как ограничения.
Provider workers и приложение не запускаются самим data-drill.

Успешный drill доказывает восстановление выбранной копии, а не произвольной даты.
PITR/WAL archive здесь не настраивается и не заявляется. Не используйте живой
PostgreSQL cluster как «изолированный» только из-за другого имени target DB:
недоверенный SQL может выполнять привилегированные операции внутри cluster.

## Шифрование и будущая внешняя копия

Restic — стандартное authenticated encrypted storage. Настоящая внешняя точка
пока не настроена. После выбора и одобрения используйте отдельные минимальные
credentials/версионирование/immutability, `RESTIC_REPOSITORY` и приватный
`RESTIC_PASSWORD_FILE` вне архива. Сначала инициализируйте репозиторий согласно
официальной документации, затем проверяйте чтение/decrypt и восстановление.
Пароль нельзя помещать в manifest, журнал или один файл с архивом.

Проверка restic repository подтверждает encryption/integrity. Она не доказывает
физическую независимость: локальный каталог и MinIO на том же сервере могут
погибнуть вместе с CRM. Эта часть должна иметь отдельное подтверждение владельца.
Age secret-export — отдельная явная OWNER offline-операция, не автоматическое
добавление `.env` в обычный архив. Прежде чем доверять secret bundle, сделайте
контролируемую проверку расшифровки на синтетическом файле, не раскрывая ключ.

Retention по умолчанию выключен. Сначала dry-run, защита минимального набора,
последней целостной DATA/FULL, последнего checksum-bound успешного drill и
источников незавершённых заданий. Для daily/weekly/monthly действуют отдельные
границы. Нельзя удалять последнюю пригодную для восстановления копию.

После отдельного разрешения автоматическое применение требует одновременно
`allowAutomaticRetention:true` в приватной host-конфигурации и включённой политики
CRM. Оно выполняется после успешного BACKUP под теми же блокировками, используя
ту же политику, что и ручной maintenance CLI. Ошибка очистки журналируется отдельно
и не повторяет уже завершённое создание копии. До такого разрешения — только dry-run.

## Перенос на другой сервер

Проверочный PostgreSQL ограничен 512 MiB PGDATA tmpfs, 768 MiB RAM и 300 секундами.
Архивы ограничены суммарным распакованным размером 4 GiB и 100000 entries;
HTTP upload по умолчанию 2 GiB. Превышение лимита останавливает проверку, а не
разрешает восстановление с ослабленной изоляцией. Для более крупных данных
нужен отдельно рассмотренный ресурсный профиль.

`recovery-install.py --drill` проверяет переносимость и удаляет тестовый
PostgreSQL после завершения. `--prepare` оставляет его работающим в карантине
с отметкой `QUARANTINED_VOLATILE`: это временная проверочная база, её данные
теряются при остановке. Не используйте её как долговечную рабочую установку.
Исходный FULL и восстановленные локальные файлы остаются на диске. Долговечный
runtime устанавливается следующим отдельным этапом из проверенного пакета.

1. Подготовьте отдельный Linux/Docker host с подходящими CPU/OS/PostgreSQL,
   ресурсными лимитами и приватным хранилищем. Не используйте живые тома.
2. Проверьте FULL, совместимость образов и свободное место. Если нужна offline
   установка, архив должен содержать docker-save; одного image ID недостаточно.
3. Доверенный `recovery-install.py` выполняет preflight и изолированную подготовку
   выбранного архива. Uploaded Compose/source/scripts остаются данными до review;
   image loading допускается только отдельным явным действием.
4. Передайте и расшифруйте отдельно защищённые секреты. Сохраните исходный
   SETTINGS_ENCRYPTION_KEY и отдельные ключи Chatwoot; не создавайте подмену ключа.
5. Проверьте DB/files/counts/историю/изображения. Затем подготовьте runtime из
   проверенного source/image, с выключенными отправителями, импортом и webhook.
6. Настройте новый домен, WEB_ORIGIN/API URLs, SMTP, provider mappings и proxy/SSL.
   Существующий reverse proxy не заменяется автоматически. БД не публикуется.
7. До DNS cutover убедитесь, что старый и новый серверы не отправляют сообщения
   и не обрабатывают одинаковые webhooks одновременно. Активация — отдельный gate.

## Production recovery и откат — отдельная согласуемая операция

UI формирует только проверенный запрос/план. Нужны точный ID/checksum архива,
оценка потери изменений после snapshot, ответственный и явное разрешение.
Перед переключением обязательны:

1. Свежая аварийная DATA/FULL текущего состояния; проверить её и сохранить вне
   заменяемых БД/томов. Не использовать выбранную старую копию как аварийную.
2. Maintenance/read-only и контролируемая остановка writers, imports, webhooks,
   email/sender workers. Зафиксировать состояние и IDs прежних resources.
3. Restore только в новые DB/storage, с проверкой версии/миграций/health и
   контрольных заказов, переписок, оплат, файлов. Не выполнять seed.
4. После независимой приёмки атомарно переключить connection/storage. Старые
   ресурсы сохранить; не чистить их в том же run.
5. При ошибке вернуть прежние connection/storage, проверить health, сохранить
   аварийную копию и журнал. Не «откатывать» удалением рабочей БД.
6. Снять maintenance и активировать интеграции только на одном сервере, с
   проверкой deduplication/idempotency и наблюдением за первыми заданиями.

В текущей разработке ни один из production-шагов не выполняется автоматически.

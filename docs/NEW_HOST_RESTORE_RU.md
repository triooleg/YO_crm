# Как восстановить YO CRM на новом сервере

Этот порядок предназначен для отдельного сервера или виртуальной машины. После
релиза цветов статусов и изменений списка клиентов зафиксируйте точную
принятую версию и выберите копию нужного состояния. В конце у вас будет
локальная CRM для проверки через браузер, со своей базой и своими файлами.
Публикация и переключение описаны отдельно в последнем разделе.

## 1. Соберите комплект у владельца

- В старой CRM откройте **Настройки → Резервное копирование**, нажмите
  **Создать копию данных** (DATA), дождитесь завершения и выберите
  **Скачать архив**. Подтвердите скачивание текущим паролем в самой CRM.
  Запишите ID, дату снимка и версию. Сохраните файл как `archive.tar.gz`.
  DATA содержит PostgreSQL и локальные файлы. FULL формата 3 тоже подходит.
  Код, образы и отдельные компоненты из FULL останутся внутри архива.
  DATA формата 2 содержит меньше контрольных данных. Для старой копии
  сверяйте записи и файлы отдельно.
- Если проверенный архив уже есть на старом хосте, выберите готовый
  `archive.tar.gz` с известными ID и результатом проверки. Порядок проверки
  описан в [основном регламенте](BACKUP_RECOVERY_RUNBOOK.md). Пример переноса
  файла с хоста приведён ниже.
- Сохраните отдельно SHA-256 **всего** файла `archive.tar.gz`, ID копии,
  дату снимка и сведения о согласованности. Для свежей завершённой копии
  возьмите контрольную сумму архива из её карточки в старой CRM. Для старой
  копии без суммы файла возьмите SHA-256 проверенного `archive.tar.gz` на
  исходном хосте. Сумма манифеста и сумма скачанного файла на вашем
  компьютере не заменяют этот эталон.
- Зафиксируйте точные ID четырёх доверенных образов `sha256:…` для PostgreSQL,
  Redis, API и Web. У PostgreSQL должна совпадать основная версия с копией, у
  всех образов — архитектура сервера. Для API и Web нужен комплект одной
  принятой версии, совместимый со схемой копии. Сверьте его с отчётом о релизе.
  Экспортируйте образы по точным ID с помощью следующего блока. Доступ к
  реестру не требуется. Восстановление использует уже загруженные образы и
  схему из снимка.
- Получите проверенный комплект **инструментов восстановления** отдельно от
  DATA/FULL. Запишите полный SHA коммита, в котором есть эта инструкция и
  `scripts/new-host-restore.py`. Если на новом сервере нет доступа к GitHub,
  администратор может передать пакет этих инструментов и его SHA-256
  отдельным доверенным каналом.

FULL не восстанавливает оригиналы внешних файлов по URL, секреты, Redis,
отдельный Chatwoot или состояние внешних сервисов. Список покрытия уточняйте
по манифесту и у владельца.

### Сохраните точные образы на старом хосте

Выполняйте этот блок как владелец на **старом** хосте после приёмки релиза.
Этот вариант рассчитан на исходный classic store. Сначала проверьте, что
вывод `docker info --format '{{.Driver}} {{json .DriverStatus}}'` на старом
хосте не содержит `io.containerd.snapshotter.v1`. Блок читает ID образов
запущенных контейнеров и пишет только в новый приватный
каталог. Сверьте имя Compose-проекта и ID с принятым релизом. Если для
сервиса найдено несколько контейнеров или контейнер отсутствует, остановитесь.

```bash
(
  set -eu
  umask 077
  EXPORT="$(mktemp -d "$HOME/yo-transfer.XXXXXXXX")"

  image_id() {
    local service="$1"
    local -a containers
    mapfile -t containers < <(docker ps -q \
      --filter 'label=com.docker.compose.project=yoleotard-crm' \
      --filter "label=com.docker.compose.service=$service")
    if [ "${#containers[@]}" -ne 1 ]; then
      printf 'Expected one running container for %s\n' "$service" >&2
      return 1
    fi
    docker inspect --type container --format '{{.Image}}' "${containers[0]}"
  }

  PG_IMAGE="$(image_id postgres)"
  REDIS_IMAGE="$(image_id redis)"
  API_IMAGE="$(image_id api)"
  WEB_IMAGE="$(image_id web)"
  printf '%s\n' "$PG_IMAGE" "$REDIS_IMAGE" "$API_IMAGE" "$WEB_IMAGE" > "$EXPORT/image-ids.txt"
  docker image save -o "$EXPORT/yocrm-images.tar" "$PG_IMAGE" "$REDIS_IMAGE" "$API_IMAGE" "$WEB_IMAGE"

  # Укажите точный путь только для уже проверенной копии на хосте.
  # Если DATA скачали через CRM, оставьте значение пустым.
  VERIFIED_ARCHIVE=''
  if [ -n "$VERIFIED_ARCHIVE" ]; then
    cp -- "$VERIFIED_ARCHIVE" "$EXPORT/archive.tar.gz"
    chmod 600 "$EXPORT/archive.tar.gz"
  fi
  cd "$EXPORT"
  printf 'Export directory: %s\n' "$EXPORT"
  sha256sum yocrm-images.tar
  if [ -f archive.tar.gz ]; then sha256sum archive.tar.gz; fi
  cat image-ids.txt
)
```

Строки `image-ids.txt` идут в порядке PostgreSQL, Redis, API, Web.
`docker inspect` выводит только ID образов. Сохраните четыре ID и ожидаемую
SHA-256 файла образов отдельно от передаваемых файлов. Сверьте SHA-256 DATA
с эталоном из проверки выбранной копии. Docker-экспорт может быть большим.
Он хранится в приватном каталоге отдельно от DATA/FULL.

## 2. Подготовьте новый Ubuntu-сервер

Установите Docker Engine 28 или новее и плагин `docker compose` из официального
APT-репозитория. Используйте раздел **Install using the apt repository**.
Для файла ключа нужен Compose с поддержкой `env_file.format: raw`
(2.30 или новее). [Официальная установка Docker Engine на Ubuntu](https://docs.docker.com/engine/install/ubuntu/).
Версия Engine нужна для внутренней сети без шлюза на хосте.
[Режим изоляции сети Docker](https://docs.docker.com/engine/network/port-publishing/#gateway-modes).

На новом сервере выполните следующие команды под выделенной учётной записью.
Ей нужен доступ к локальному Docker. Доступ к Docker эквивалентен
административному, поэтому его предоставляет администратор.

```bash
sudo apt install python3 git
docker version
docker compose version
docker context show
umask 077
mkdir -p "$HOME/yo-recovery/incoming"
chmod 700 "$HOME/yo-recovery" "$HOME/yo-recovery/incoming"
df -h "$HOME/yo-recovery" /var/lib/docker
```

Нужно место под исходный архив, временную распаковку, папку загрузок, образы
и распакованную БД. Лимит валидатора — 4 ГиБ и 100 000 элементов. При ошибке
лимита остановитесь и согласуйте ресурсный профиль с администратором.

### Перенесите файл с Windows

В PowerShell подставьте адреса серверов, экспортный каталог со старого хоста
и путь к DATA/FULL. При первом SSH сверьте отпечаток ключа каждого сервера.
Подготовьте каталог `incoming` на новом хосте как показано выше.

```powershell
$OldServer = 'operator@192.0.2.10'
$NewServer = 'operator@203.0.113.10'
$OldExport = '/home/operator/yo-transfer.REPLACE'
$Files = Join-Path $env:USERPROFILE 'YO-Recovery-Transfer'
New-Item -ItemType Directory -Force -Path $Files | Out-Null
Set-Location -LiteralPath $Files

scp "${OldServer}:${OldExport}/yocrm-images.tar" .
scp "${OldServer}:${OldExport}/image-ids.txt" .
# Для уже проверенного файла на старом хосте используйте следующую команду.
# scp "${OldServer}:${OldExport}/archive.tar.gz" .
# Если DATA скачали через CRM, положите его сюда как archive.tar.gz.

Get-FileHash -Algorithm SHA256 -LiteralPath '.\archive.tar.gz', '.\yocrm-images.tar'
# Сверьте обе SHA-256 с сохранённым эталоном и только тогда продолжайте.
scp '.\archive.tar.gz' '.\yocrm-images.tar' '.\image-ids.txt' "${NewServer}:yo-recovery/incoming/"
ssh $NewServer
```

### Закрепите исходники инструментов и проверьте Docker

Получите URL доверенного репозитория и SHA коммита инструментов у
администратора. Если он передал отдельный проверенный пакет, сверьте
его SHA-256 и используйте его каталог вместо `toolkit`.

```bash
cd "$HOME/yo-recovery"
git clone '<доверенный-URL>' toolkit
git -C toolkit checkout --detach '<полный-SHA-коммита-инструментов>'
git -C toolkit rev-parse HEAD
test -f toolkit/scripts/new-host-restore.py
```

Сверьте SHA коммита. Следующие команды предназначены для нового Ubuntu с
локальным системным Docker. Выполните блок целиком перед `docker image load`.

```bash
(
  set -eu
  cd "$HOME/yo-recovery"
  unset DOCKER_HOST DOCKER_CONTEXT DOCKER_CONFIG
  CTX=default
  test "$(docker --context "$CTX" context inspect "$CTX" --format '{{.Endpoints.docker.Host}}')" = 'unix:///var/run/docker.sock'
  python3 toolkit/scripts/new-host-restore.py --check-docker --docker-context "$CTX"
  docker --context "$CTX" info --format '{{.Driver}} {{json .DriverStatus}}'
)
```

Ожидайте `default` от preflight. Скрипт проверяет локальный Linux Engine и
отсутствие контейнеров, томов и сетей рабочего проекта `yoleotard-crm`.
При любой ошибке остановитесь до загрузки образов.

### Выберите совместимое хранилище образов на новом хосте

Этот экспорт со старого **classic** Docker фиксирует ID конфигураций образов.
На свежем Docker Engine 29 по умолчанию используется containerd. При импорте
того же архива `docker image inspect .Id` может вернуть SHA манифеста OCI
вместо SHA конфигурации. Целостность архива и локальный ID проверяются
раздельно. Для описанного classic-экспорта используйте classic store и
проверяйте каждый локальный ID против исходного. [Хранилище containerd в Docker Engine](https://docs.docker.com/engine/storage/containerd/).

Если предыдущий блок показывает `overlay2` без `io.containerd.snapshotter.v1`,
переходите к загрузке. Если включён containerd, этот вариант применяйте только
на **новом пустом Ubuntu-хосте**. Убедитесь, что preflight выше прошёл, а
`docker --context default ps -aq`, `docker --context default image ls -aq`
и `docker --context default volume ls -q` ничего не выводят. Смена
хранилища скрывает ресурсы другого backend, поэтому для занятого хоста
выберите отдельную чистую машину.

На новом пустом хосте откройте `sudoedit /etc/docker/daemon.json`. Если файл
уже есть, добавьте `containerd-snapshotter` в существующий объект `features`
с сохранением остальных настроек. Для пустого файла содержимое такое.

```json
{
  "features": {
    "containerd-snapshotter": false
  }
}
```

Проверьте файл, перезапустите только Docker нового хоста и заново выполните
preflight. Убедитесь, что драйвер `overlay2` и маркер containerd отсутствует.
Если это условие не выполнено, остановитесь до импорта.
[Параметры dockerd](https://docs.docker.com/reference/cli/dockerd/).

```bash
sudo dockerd --validate --config-file /etc/docker/daemon.json && sudo systemctl restart docker
```

Если исходный экспорт сделан из другого backend или локальные ID после
импорта отличаются, остановитесь. Для такого пакета нужна отдельная
проверенная привязка каждого исходного образа к локальному digest через
метаданные экспорта. Имя, тег и строка из вывода `docker load` сами по себе
такую привязку не доказывают.

### Проверьте архивы и загрузите образы

Выполните блок только после подтверждения classic store на новом хосте.
Подставьте две SHA-256, сохранённые независимо от полученных файлов.
Блок повторно проверяет тот же явно выбранный локальный Docker перед импортом.

```bash
(
  set -eu
  cd "$HOME/yo-recovery"
  unset DOCKER_HOST DOCKER_CONTEXT DOCKER_CONFIG
  CTX=default
  test "$(docker --context "$CTX" context inspect "$CTX" --format '{{.Endpoints.docker.Host}}')" = 'unix:///var/run/docker.sock'
  python3 toolkit/scripts/new-host-restore.py --check-docker --docker-context "$CTX"
  store="$(docker --context "$CTX" info --format '{{.Driver}} {{json .DriverStatus}}')"
  case "$store" in
    *io.containerd.snapshotter.v1*) exit 1 ;;
    'overlay2 '*) ;;
    *) exit 1 ;;
  esac
  cd incoming
  chmod 600 archive.tar.gz yocrm-images.tar image-ids.txt
  DATA_SHA='<64-символа-SHA-256-копии>'
  IMAGES_SHA='<64-символа-SHA-256-экспорта-образов>'
  printf '%s  archive.tar.gz\n%s  yocrm-images.tar\n' "$DATA_SHA" "$IMAGES_SHA" | sha256sum -c -
  mapfile -t images < image-ids.txt
  test "${#images[@]}" -eq 4
  for image in "${images[@]}"; do
    [[ "$image" =~ ^sha256:[a-f0-9]{64}$ ]]
  done
  docker --context "$CTX" image load -i yocrm-images.tar
  for image in "${images[@]}"; do
    test "$(docker --context "$CTX" image inspect --format '{{.Id}}' "$image")" = "$image"
    printf '%s\n' "$image"
  done
)
```

Сверьте четыре напечатанных ID с отдельно сохранённым списком в порядке
PostgreSQL, Redis, API, Web. В команду восстановления вводятся именно
проверенные **локальные** ID. При несовпадении суммы или ID остановитесь.
Образы загружаются из отдельного экспорта владельца. Содержимое DATA/FULL
не используется как источник исполняемых образов.

### Решите, нужен ли оригинальный ключ

Для проверки локальных заказов, клиентов и файлов можно начать с
автоматически созданным изолированным ключом. Зашифрованные настройки
каналов с ним недоступны. Чтобы проверить сохранность этих настроек и затем
использовать их при отдельно одобренном переносе, нужен **исходный**
`SETTINGS_ENCRYPTION_KEY` от владельца. Получайте его только по приватному
каналу владельца или из его закрытого хранилища секретов. Перенесите ключ на
новый сервер в один приватный файл с правами `0600`, принадлежащий оператору,
с одной строкой значения. В командной строке указывайте только путь. Ключ
доступен администратору Docker и сохраняется в приватном `api.env`. Сам отчёт
содержит только тип ключа. Файл и каталог держите вне Git, общих папок и чатов.

## 3. Восстановите локальную копию

В SSH на новом сервере запустите команду. Замените все значения в угловых
скобках. Для ключа владельца допишите
`--settings-key-file "$HOME/yo-recovery/owner-settings.key"`.

```bash
cd "$HOME/yo-recovery"
python3 toolkit/scripts/new-host-restore.py \
  --archive "$PWD/incoming/archive.tar.gz" \
  --sha256 '<64-символа-из-сообщения-владельца>' \
  --target "$PWD/restored" \
  --docker-context default \
  --postgres-image 'sha256:<ID-PostgreSQL>' \
  --redis-image 'sha256:<ID-Redis>' \
  --api-image 'sha256:<ID-API>' \
  --web-image 'sha256:<ID-Web>'
```

Дождитесь `"status": "PASS"`. Сохраните `restored/restore-report.json` и
сверьте ID и SHA-256 копии. `sourceConsistent: false` означает, что автономная
команда не удостоверяла условия, в которых работал исходный сервер при
снятии копии. Отдельная квитанция владельца отвечает за эту часть.

PostgreSQL хранится в новом именованном томе, файлы — в `restored/uploads`.
Скрипт проверяет известные файловые ссылки, ограничения БД и доступные
отпечатки, проверяет точный путь единственного bind uploads у остановленного контейнера,
затем запускает API в режиме `recovery-isolated` и проверяет HTTP 503
для вебхука и изменения заказа. Redis локальный и временный. Контейнеры
находятся во внутренней сети без шлюза. Приложение запускается из проверенных
образов без seed, миграций, импорта и подключения к провайдерам.

Если запуск завершился ошибкой, сохраните отчёт, если он создан, и название
этапа. Неудачная попытка удаляет свой новый проект и его том PostgreSQL.
Папка подготовки, включая распакованные uploads, остаётся приватной. Для
повторной попытки выберите новый каталог, например `restored-2`.
Если в отчёте `cleanup: FAILED_OPERATOR_ACTION_REQUIRED`, администратор
сначала проверяет созданные ресурсы по полям `project` и `databaseVolume`.
Старые или чужие проекты и тома не входят в очистку.

## 4. Откройте CRM в браузере и проверьте перезапуск

Перед открытием реальной копии поместите Ubuntu и компьютер с браузером в
изолированную LAN без доступа в интернет. Подойдёт отдельный коммутатор
или роутер с физически отключённым WAN. Оставьте подключение по локальному
IP для SSH. На обеих машинах отключите остальные подключения, включая Wi-Fi,
мобильный модем и VPN. При необходимости задайте адреса вручную, например
192.168.77.10/24 на Windows и 192.168.77.20/24 на Ubuntu. Поля шлюза и DNS
оставьте пустыми. В SSH-команде используйте локальный адрес Ubuntu.
Отключите прокси и автоматическую настройку прокси
на компьютере с браузером. Проверьте отсутствие маршрутов по умолчанию.

```powershell
Get-NetRoute -DestinationPrefix '0.0.0.0/0','::/0' -ErrorAction SilentlyContinue
```

```bash
ip -4 route show default
ip -6 route show default
```

Команды должны вернуть пустой результат. Если маршрут остался, не открывайте
реальную копию.

Откройте второе окно PowerShell. Эта команда соединяет порт на вашем
компьютере с локальным портом нового сервера и одновременно запускает
там временный туннель CRM. Оставьте окно открытым.

```powershell
$NewServer = 'operator@192.168.77.20'
ssh -t -o ExitOnForwardFailure=yes -L 127.0.0.1:33502:127.0.0.1:33502 $NewServer 'cd yo-recovery && python3 toolkit/scripts/new-host-restore.py --target restored --open'
```

Затем откройте новое приватное окно браузера. Проверьте,
что внешний сайт `https://example.com/?yo-recovery-egress-check` не
открывается с отключённой сетью, а `http://127.0.0.1:33502/api/health`
через SSH-туннель возвращает `ok: true`. Запишите оба результата и только
после этого откройте `http://127.0.0.1:33502/` и войдите учётной записью
из снимка. Сеть сохраняйте изолированной до закрытия браузера.
Docker ограничивает доступ контейнеров к провайдерам. Проверка браузера
нужна отдельно, поскольку он может запросить сохранённый удалённый файл.

Сверьте несколько известных клиентов, заказов, оплат и переписок, откройте
одно локальное вложение. Проверяйте данные чтением. Для закрытия туннеля
нажмите Ctrl+C. Затем в первом SSH-окне подставьте `dockerContext` и `project`
из отчёта. `stop` и `start` повторно используют уже проверенные контейнеры
и их хранилища.

```bash
cd "$HOME/yo-recovery/restored"
CTX='<dockerContext-из-отчёта>'
PROJECT='<project-из-отчёта>'
docker --context "$CTX" compose -p "$PROJECT" --env-file compose.env -f compose.json stop
docker --context "$CTX" compose -p "$PROJECT" --env-file compose.env -f compose.json start --wait --wait-timeout 90
docker --context "$CTX" compose -p "$PROJECT" --env-file compose.env -f compose.json ps
```

Снова откройте туннель. Сверьте те же записи и файл. Если свободен другой
порт, измените обе стороны SSH `-L` и передайте его в `--open --port`.
Отметьте дату, версию, архив и результаты сверки. Туннель, DNS, TLS и
провайдеры — отдельные вещи. Проверка локальной копии подтверждает доступ
к выбранному снимку и сохранность после пересоздания контейнеров.

## 5. Отдельная ручная операция для публичного TLS и одного сервера записи

Этот этап выполняет администратор после отдельного разрешения владельца
по [основному регламенту аварийного восстановления](BACKUP_RECOVERY_RUNBOOK.md#production-recovery-и-откат--отдельная-согласуемая-операция).
Восстановительный Compose рассчитан на карантин. Для публичной работы нужен
отдельно проверенный боевой комплект с TLS, секретами, резервным копированием
и проверкой здоровья. DNS, переключение и активация интеграций требуют
ручного решения.

1. Зафиксируйте время остановки записей, ответственных, прежние DNS и proxy,
   идентификаторы старых ресурсов, окно проверки и критерий отката. Проверьте
   TLS для нужного домена на согласованном reverse proxy. Публикуйте только
   HTTPS. Оставьте PostgreSQL и Redis внутри сети.
2. Перед финальным снимком остановите записи на старой CRM и отключите на ней
   обработку webhook, фоновые импорты и отправители. Сделайте свежую
   согласованную копию, проверьте её и сохраните независимо от обоих серверов.
   Если между репетицией и остановкой были изменения, переносите финальный
   снимок в новые ресурсы и повторите приёмку.
3. Администратор готовит публичный runtime из принятого комплекта,
   подставляет оригинальный ключ владельца и отдельно согласованные секреты,
   проверяет схему, файлы, URL, TLS и восстановление. Пока старый сервер
   способен писать, новый остаётся в режиме проверки.
4. Переключите proxy/DNS и проверьте домен, сертификат, вход и контрольные
   записи. После отключения старого сервера как источника записи включите
   запись и согласованные интеграции только на новом. Учтите кэш DNS и
   повторы webhook. Проверьте первую обработку и отсутствие дублей.
5. До первых записей на новом откат — возврат proxy/DNS к прежней проверенной
   цели и восстановление её роли единственного сервера записи. После первых
   записей сначала снова остановите запись и согласуйте перенос изменений.
   Простое переключение назад в этот момент может потерять новые данные.


### Что администратор сверяет в боевом комплекте

| Настройка | Что проверить перед открытием записи |
| --- | --- |
| PostgreSQL | Используйте только принятый финальный снимок. Если переносите его именованный том, сначала остановите карантинный PostgreSQL. Сверьте имя `databaseVolume` из отчёта, подключите этот том как существующий внешний том к `/var/lib/postgresql/data` и сохраните основную версию PostgreSQL. Два процесса PostgreSQL не должны использовать один том. |
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `DATABASE_URL` | Проверьте фактическое имя БД и рабочую роль в восстановленном кластере. Укажите их в `DATABASE_URL` API через внутреннее имя PostgreSQL. Изменение `POSTGRES_*` в Compose само по себе не меняет роль или пароль в уже инициализированном томе. Боевой доступ API и права проверяет администратор. |
| `UPLOADS_DIR` | Подключите принятый приватный каталог `restored/uploads` как хранилище API либо перенесите его с проверкой файловых SHA-256. Путь внутри API обычно `/app/uploads`. Проверьте владельца и права чтения и записи. Каталог старого сервера и пустой том здесь не подходят. |
| `REDIS_URL`, `BACKUP_STORAGE_PATH` | Укажите Redis нового сервера и отдельное приватное хранилище резервных копий. Включение резервирования проверьте по основному регламенту. |
| `WEB_ORIGIN`, `API_INTERNAL_BASE_URL`, `API_PORT` | Укажите точный публичный origin `https://<домен>` в API, внутренний адрес `http://api:4500/api` в Web и согласованный порт API. Проверьте, что принятый образ Web использует этот внутренний маршрут для `/api/*`. Прокси должен передавать правильный Host и признак HTTPS. |
| `NODE_ENV`, `APP_ENV`, `AUTH_DISABLED`, `ALLOW_RESTORE` | Установите `NODE_ENV=production`, `AUTH_DISABLED=false`, `ALLOW_RESTORE=false`. До приёмки и остановки записи на старом сервере оставьте `APP_ENV=recovery-isolated` или держите боевой API остановленным. Снятие карантина является отдельным ручным шагом. |
| `SETTINGS_ENCRYPTION_KEY` и провайдеры | Используйте исходный ключ владельца и отдельно согласованные секреты. До разрешённой активации блокируйте внешний трафик и входящие webhook. Проверьте, где находятся очереди, подключаемые провайдеры и фоновая синхронизация, до включения egress. |

Проверьте TLS до смены DNS с компьютера, которому доступен новый reverse
proxy. `--resolve` направляет запрос на новый IP и сохраняет правильные
Host и TLS SNI. Укажите свои значения, без отключения проверки сертификата.

```bash
DOMAIN='crm.example.org'
NEW_IP='203.0.113.10'
curl --fail-with-body --silent --show-error \
  --resolve "$DOMAIN:443:$NEW_IP" "https://$DOMAIN/api/health"
curl --fail --silent --show-error --output /dev/null --write-out '%{http_code}\n' \
  --resolve "$DOMAIN:443:$NEW_IP" "https://$DOMAIN/"
curl --silent --show-error --output /dev/null --write-out '%{http_code}\n' \
  --resolve "$DOMAIN:443:$NEW_IP" "https://$DOMAIN/api/auth/me"
```

Ожидайте `ok: true` и `up` для `postgres`, `redis` и `uploads` в health,
HTTP 200 на `/` и HTTP 401 на `/api/auth/me` без сессии. Сверьте `version`
и `revision` с принятым комплектом. После смены DNS повторите проверки без
`--resolve`. Проверьте вход, контрольный заказ и локальное вложение через
HTTPS. Пока запись не разрешена, проверяйте только чтение. После ручной
активации выполните отдельно согласованную проверку записи и интеграций.

Автоматический тест этого комплекта проверяет карантин, loopback, чтение
снимка, блокировку изменений и сохранность после пересоздания контейнеров.
Публичный TLS, DNS, перенос реальных секретов, совместимость выбранного
релизного комплекта и активация единственного сервера записи принимаются
администратором отдельно.

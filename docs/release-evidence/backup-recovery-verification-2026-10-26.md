## Что расширено

- FULL v3: DATA, исходники, миграции, Compose, `.env.example`, инструкции,
  точные runtime image IDs; отдельный offline-режим включает docker-save.
- Задания, идемпотентность, lease/heartbeat, восстановление после потери
  исполнителя, расписание, прогресс, аудит и локальный каталог с manifest.
- API/UI создания, проверки, приватного скачивания, загрузки в карантин,
  запуска изолированного drill и построения плана восстановления.
- Retention с dry-run и защитой проверенных/используемых копий; подготовленное
  шифрованное restic-хранилище и отдельный явный age export секретов.

Автоматический retention использует ту же политику после завершённого BACKUP
под исходными блокировками. Требует одновременно host `allowAutomaticRetention:true`
и DB-политики `enabled:true`, по умолчанию не выполняется. Ошибка очистки не
повторяет успешно созданную копию. Внешняя отправка сейчас не активирована.

API расширен обратно совместимо в `/api/admin/backups`: `overview`, `journal`,
`upload`, `:id/download`, `:id/drill`, `:id/recovery-plan`; исходные create/list/
settings/verify и запрет production restore сохранены. Доступ OWNER/ADMIN,
повторный текущий пароль для чувствительных действий.

## Ограничение ресурсов и недоверенные архивы

SQL загружается только в свежий изолированный PostgreSQL: внутренний network,
нет published ports/production mounts, 768 MiB памяти, 1 CPU, 128 PIDs,
512 MiB PGDATA tmpfs, ограниченные temp/shm/output и общий deadline 300 секунд.
Проверены фактические cgroup/tmpfs ограничения и уничтожение дочерних процессов
после потери исполнителя. Выгруженный source/Compose автоматически не исполняется.

Импорт проверяет суммарное вложенное распакованное содержимое, число файлов,
время, свободное место, PAX/path metadata, ссылки, special files, дубли ключей
JSON и checksum. Импортированные sidecar-файлы доверия отвергаются. SHA256
подтверждает целостность, а не происхождение: unsigned manifest не может сам
доказать согласованность snapshot.

`--prepare` оставляет проверочный PostgreSQL в карантине на ограниченном tmpfs.
Он явно помечен `QUARANTINED_VOLATILE`, данные теряются при остановке. Это не
готовая долговечная production-установка. Постоянная установка из FULL,
подключение отдельно сохранённых ключей и переключение интеграций выполняются
по [регламенту](../BACKUP_RECOVERY_RUNBOOK.md) после review. Исходный архив
остаётся долговечным источником восстановления.

Legacy restore теперь также проверяет реальную bounded-конфигурацию до SQL.
Весь SQL-stage имеет общий лимит 300 секунд; при сбое supervisor завершает
только точный проверенный sandbox ID, включая серверные дочерние процессы.
Standalone lease360 секунд перекрывает рабочий лимит. Унаследованные global/job
leases с коротким оставшимся временем отклоняются до SQL: реальные проверки
60/120/600 секунд PASS. Программа передаётся через `bash -c` с отдельным stdin,
чтобы Docker exec не поглощал оставшиеся команды.

## Дополнение: выбор переноса на рабочий компьютер

Реализована настройка MANUAL/AUTOMATIC с папкой `D:\YO_CRM_Backups` и интервалом
5–1440 минут (по умолчанию 30). Создание архивов остаётся в существующем
BackupsModule и host agent; Windows helper только скачивает готовые архивы.
Ручное скачивание через браузер сохранено; окончательное размещение ручного
скачивания управляется настройками браузера.

Для автоматического режима подготовлен явный установщик пользовательской
задачи Windows. Браузер может быть закрыт, пользователь должен оставаться
вошедшим в Windows. Переключение в CRM само по себе задачу не устанавливает.
Сопряжение и отзыв требуют свежего пароля OWNER/ADMIN; одноразово показанный
90-дневный токен разрешает только чтение архивов, проверяется при каждом запросе
и хранится локально через DPAPI CurrentUser. На сервере хранится только hash.
Предел — 20 активных компьютеров и 100 записей реестра; при заполнении удаляются
только самые старые неактивные записи реестра, журнал аудита сохраняется.

Скачивание проверяет точные размер/SHA256 и не перезаписывает конфликтующий
архив. Каждая попытка использует собственный UUID temporary: файлы, оставшиеся
после аварии, не блокируют повтор и не удаляются автоматически. ACL новых
архивов ограничены текущим Windows-пользователем и SYSTEM. DPAPI защищает
настройку с токеном; сами локальные архивы остаются незашифрованными.

Локальные проверки: **50/50** helper tests PASS, включая настоящий Windows DPAPI
roundtrip и ACL исключительно синтетических данных, совместимый с Python 3.9
`lstat()` и позднее завершение старого архива. Завершённый обход списка сбрасывает
cursor для нового ограниченного обхода (до 100 записей за интервал), чтобы
поздно завершённые архивы не пропускались. Полный Python suite:
**146 тестов, 138 PASS / 8 ожидаемых platform/opt-in skips**. Регрессия гонки
enqueue/retention дополнительно прошла на настоящем PostgreSQL с Prisma:
принятый drill защищает исходный архив, начатое удаление отклоняет новый drill,
в том числе при alias. Все временные тестовые проекты удалены; контейнеры
production сохранили прежние ID, образы и время старта, остались healthy.

## RPO/RTO и граница production

Фактическое RPO сейчас определяется существующими установленными production
процедурами: новая автоматика ещё не установлена, обещание ежедневных копий
не даётся. Контрольная точка данных — 13:32:36 UTC. PITR не заявляется.

В production recovery обязательны свежая аварийная копия, проверка её
пригодности, maintenance, новые DB/storage, контрольные записи/health,
сохранение прежних подключений/томов и готовый откат. DNS/traffic cutover и
возобновление единственного набора senders — отдельная одобренная операция.

# Инженерные skills Codex в YO_crm

Project-local skills находятся в `.agents/skills/` и версионируются вместе с
репозиторием. `skills-lock.json` фиксирует источник и хеши upstream skills.
Правила YO_crm из `AGENTS.md`, `CONTEXT.md` и `docs/decisions/` имеют приоритет
над общими рекомендациями установленного пакета.

В Codex явный вызов делается через `$skill-name` или через выбор в `/skills`.
Upstream-документы иногда называют orchestration skills в slash-нотации; для
этой установки используйте Codex-синтаксис, например:

```text
$diagnosing-bugs

После обновления Inbox повторно появляется уже удалённая реакция.
```

Обычный запрос естественным языком также подходит для model-invoked skills:
Codex сам выбирает минимальный достаточный процесс.

## Уровень процесса

### Level 1 — простая правка

Текст, иконка, опечатка или изолированный CSS. Codex изучает место изменения,
правит напрямую и выполняет узкую проверку. Полная цепочка skills не нужна.

### Level 2 — обычная функция

Новый фильтр, форма, API action или небольшая интеграция. Процесс: анализ →
реализация → тесты → review. `tdd` применяется там, где поведение можно надёжно
зафиксировать тестом.

### Level 3 — сложная функция

Переработка Inbox/Orders, новая Meta-интеграция, планировщик производства или
платёжный контур. Обычно начать с `$grill-with-docs`, затем при необходимости
пройти `$to-spec` → `$to-tickets` → `$implement` → `$code-review`.

### Level 4 — большая инициатива

Новая AI-архитектура, смена messaging-платформы, крупная миграция или новый
архитектурный слой. Использовать `$wayfinder`, чтобы сначала снять
неопределённость и оформить решения, а затем перейти к specification и tickets.

## Основные команды

### `$ask-matt`

Маршрутизатор: подсказывает подходящий skill или последовательность.

```text
$ask-matt

Я хочу полностью переработать производственное планирование. Какой процесс
подойдёт и с чего начать?
```

### `$grill-with-docs`

Уточняет сложную идею вопросами и поддерживает доменную документацию. Подходит,
когда важные решения ещё не приняты.

```text
$grill-with-docs

Хочу добавить Production Scheduler для заказов Yoleotard.
```

### `$to-spec`

Превращает уже подробное обсуждение в проверяемую specification. По настройке
этого репозитория публикация означает GitHub Issue, поэтому внешняя запись
выполняется только когда текущий запрос её разрешает.

### `$to-tickets`

Разбивает spec/plan на небольшие tracer-bullet tickets, указывает зависимости и
критерии приёмки. Не отправляет их в GitHub без разрешения.

### `$implement`

Реализует утверждённую specification или ticket. Сохраняет контракты проекта,
использует TDD на подходящих seams и завершает работу review. Встроенный
`code-review` дополняет, но не заменяет пять обязательных ролей из
`.agents/README.md`. В YO_crm команда готовит незакоммиченный diff и не создаёт
commit, push или deploy без явного разрешения пользователя.

Скопированный `$code-review` сравнивает committed history. Если commit не разрешён,
Codex проверяет полный staged/unstaged/untracked diff напрямую по двум тем же
осям (стандарты и spec), а затем запускает обязательные project review-роли.

### `$diagnosing-bugs`

Для сложных, плавающих или повторных ошибок. Цикл: воспроизведение → минимальный
красный сигнал → гипотезы → инструментирование → корневая причина → исправление
→ regression test.

### `$improve-codebase-architecture`

Проводит архитектурный survey и ранжирует возможности. Результат сначала
показывается как отчёт; большой refactor не начинается автоматически.

### `$wayfinder`

Для инициатив, которые не помещаются в одну сессию. Создаёт карту решений и
снимает неопределённость; реализация начинается отдельным последующим процессом.

### `$handoff`

Создаёт компактную переносимую передачу контекста: состояние, решения,
завершённое, оставшееся, блокеры, изменённые файлы, проверки и следующий шаг.
Она не заменяет обязательное обновление канонического `CHAT_HANDOFF.md` после
значимой реализации или deployment.

### `$wait-what`

Просит агента заново объяснить последнюю мысль простым языком и с недостающим
контекстом.

## Остальные установленные skills

- `$triage` — проверяет входящие чужие issues/PR и готовит исполнимое описание.
- `$prototype` — создаёт изолированный выбрасываемый прототип для ответа на один
  вопрос о поведении или интерфейсе.
- `$research` — исследует вопрос по первичным источникам и сохраняет результат.
- `$tdd` — ведёт короткими циклами red → green → refactor.
- `$domain-modeling` — уточняет термины, обновляет `CONTEXT.md` и помогает с ADR.
- `$codebase-design` — проектирует глубокие модули, интерфейсы и seams.
- `$code-review` — проверяет diff одновременно против стандартов и исходной spec.
- `$resolving-merge-conflicts` — разрешает merge/rebase-конфликты по намерению.
- `$wizard` — готовит пошаговый сценарий для действий, которые может выполнить
  только человек; не заменяет доступные агенту действия.
- `$grilling` — базовая дисциплина строгого интервью.
- `$grill-me` — интервью без записи доменной документации.
- `$writing-for-agents` — правила написания `SKILL.md`, `AGENTS.md` и документов
  для агентов.
- `$setup-matt-pocock-skills` — повторный setup нужен только при смене tracker или
  структуры domain docs.

## Project-specific skills

Codex выбирает их автоматически при работе с соответствующим модулем:

- `yoleotard-orders`
- `yoleotard-measurements`
- `yoleotard-production`
- `yoleotard-payments`
- `yoleotard-messaging`
- `yoleotard-crm-ui`

Они содержат короткий процесс и ссылки на реальные источники, а не копию всей
бизнес-логики.

## Как создать новый skill

1. Найти похожий skill в `.agents/skills/`.
2. Изучить его `SKILL.md`, metadata и дополнительные файлы.
3. Сформулировать одно узкое назначение.
4. Выбрать тип: user-invoked orchestration или model-invoked discipline.
5. Для user-invoked создать `agents/openai.yaml` с
   `policy.allow_implicit_invocation: false`. Для model-invoked не добавлять этот
   запрет и написать точное `description` с условиями срабатывания.
6. Не копировать правила из `AGENTS.md` и определения из `CONTEXT.md`.
7. Ссылаться на canonical documentation и исходный код.
8. Описать trigger conditions, ожидаемый процесс и проверяемое условие
   завершения.
9. Зафиксировать ограничения и действия, требующие разрешения.
10. Проверить skill на реальной небольшой задаче и документировать пример.

## Обновление

Из корня репозитория:

```powershell
git status --short
npx skills update --project --yes
git diff -- .agents/skills skills-lock.json
```

После обновления проверить, что каталоги `yoleotard-*` сохранены, inspect diff
upstream-копий, выполнить проверки из изменённых skills и базовые проверки
проекта. Не принимать обновление поверх локальных изменений вслепую.

Для загрузки upstream baseline на новой машине используется lock-файл:

```powershell
npx skills experimental_install
```

Эта команда не является точным восстановлением YO_crm-версии skills: текущий
формат lock-файла не фиксирует Git commit источника, а хеши относятся к upstream
до локальных адаптаций. Точное состояние восстанавливается checkout нужной
ревизии самого репозитория YO_crm, где `.agents/skills/` хранится целиком.
Наблюдавшийся при установке commit, список адаптаций и порядок проверки записаны
в `docs/agents/upstream-skills.md`; после загрузки baseline всегда сравнивайте
хеши и полный diff.

## Связь с существующим DAG

Matt skills выбирают глубину процесса, уточняют требования и готовят spec/tickets.
Существующий `tools/dag` и `.codex/agents` остаются механизмом параллельного
исполнения крупных задач. Их worktree, role и INTEGRATOR-правила не заменяются
командой `$implement`.

## Git и безопасность

Разделяйте review на три группы: upstream `.agents/skills/*`, настройка и docs,
project-specific `yoleotard-*`. Перед commit убедитесь, что diff не содержит
`.env`, ключей, токенов, паролей, банковских реквизитов, SSH-материалов и данных
клиентов. Автоматический commit этой интеграцией не выполняется.

# Резерв номера заказа на сайте

Задача для YO CRM и WordPress CheckoutV2. Сейчас AJAX корзины резервирует товар, а CRM выделяет номер после получения заказа. WordPress использует отдельный идентификатор в назначении банковского платежа.

1. CRM: добавить авторизованный запрос резерва с ключом аккаунта сайта и непрозрачным идентификатором корзины. Выделять номер под тем же блокированием, что и при создании заказов. Записать номер, время создания и состояние резерва. Повтор запроса возвращает тот же номер. Пропуски после истечения резерва допустимы: выданные номера не выдавать повторно.
2. WordPress: запрашивать резерв на сервере асинхронно после первого успешного резерва товара. Хранить связь с серверной сессией корзины; повторное добавление или открытие другой вкладки не создаёт новый номер. Корзина может открыться сразу, но создание банковского счёта ждёт подтверждённого номера. При недоступной CRM показать ошибку и дать повторить запрос с тем же ключом.
3. До создания банковского счёта связать резерв с неизменяемым идентификатором оформления. Фиксировать точное назначение платежа и ID каждой попытки отдельно. Истечение резерва товара не должно лишить уже начатый платёж номера.
4. При импорте оплаченного заказа CRM подтверждает принадлежность резерва аккаунту и оформлению и использует его номер в транзакции записи. Старые интеграции без резерва продолжают работать. Резерв без оплаты не создаёт заказ и не влияет на финансы и отчётность.
5. Проверить гонки двух корзин и ручного заказа, повторные запросы, смену года по Киеву, истечение резерва до и после выставления счёта, недоступность CRM, успешную оплату не последней попытки и повтор webhook. Сначала выпускать совместимое обновление CRM, затем плагин. Проверить на тестовом заказе цепочку корзина → Monobank → CRM.

## Выпуск и откат

1. На тестовой CRM применить миграцию 20261112190000_website_order_number_reservations. Со старым Checkout проверить обычный импорт заказа без numberReservation и merchantReference.
2. Подключить кандидат Checkout к тестовой CRM. В браузере добавить товар в корзину и записать выданный номер. Провести карточную оплату через тестовый Monobank, сверить номер в назначении и в CRM. Повторить доставку события и убедиться, что оплата сохранена один раз.
3. Выпустить CRM и применить миграцию до обновления Checkout. Проверить доступность API и приём прежнего формата заказа. Затем выпустить Checkout и проверить получение первого резерва.
4. После выдачи первого резерва сохранить таблицу резервов и сборку CRM, которая учитывает её в общей последовательности. Старые сборки CRM могут повторно выдать номер и отклонить новые поля в уже отправленных заказах. При остановке выкладки оставить совместимый API для завершения начатых оплат. Перед откатом плагина проверить, что его версия может обработать уже созданные карточные попытки.
